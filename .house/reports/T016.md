# T016: local small LLM as a grounded reader for weak fields (profile `llm`)

- **Agent / model:** coder (Claude Sonnet 5.5)
- **Branch / commits:** task/T016-local-llm-reader (cut from task/T014-scan-recipes); hashes at the end
- **Date:** 2026-11-21

## Goal
D-015/D-021: an optional local model that fills only what the recipes could not read, grounded and never
overriding a confident value. Task file: `.house/tasks/T016-local-llm-reader.md`. D-021 (mentors): LLM or no LLM both
score the maximum, so `llm` ships opt-in and only matters if it raises F1 / robustness at an acceptable time cost.

## Spike (before building)
Machine: Intel i5-1035G1 (4 cores / 8 threads, 15 W, 1.0 GHz base), 16 GB, no GPU, Windows 11, Python 3.13.17.
The machine was shared with 3-4 other agents running OCR and test suites during every measurement, so all times are
pessimistic and noisy (the same model varied 2x between runs). Bench for the grader laptop: re-measure there.

**Runtime.** `llama-cpp-python 0.3.36` installs from PyPI / the project CPU index as a **prebuilt wheel**
(`py3-none-win_amd64`, 7.8 MB, ctypes over llama.cpp; works on Python 3.13, AVX2 build). No compiler needed, no
fallback required. The JSON-schema grammar (`response_format`) constrains the answer, so the output is always valid JSON.
Threads: 4 was about 1.7x faster than 8 on this 4-core CPU under load (0.6B prompt speed 37 tok/s at 3 threads vs 18 at 8).

**Models (all GGUF, all Apache-2.0).** Task: 5 scans (pel_0004, pel_0009, pel_0010, odw_0001, odw_0005), the weak
fields (principal name / natural person, attorney names, attorney PESELs, signers; appellant, authority, BZP number,
procedure number, first-charge id), 25 questions, a generic transcribe-with-quote prompt, 1-2 pages of OCR text
(750-2200 prompt tokens). "grounded" = answers whose quote was found in the page text.

| model | file / size | load | s/doc (5 docs) | peak RAM | accuracy (25 q) | grounded / ungrounded |
|---|---|---|---|---|---|---|
| Qwen3-0.6B Q8_0 | 0.64 GB | 1.7 s | 109 | 1.7 GB | 11/25 | 19 / 5 |
| Bielik-1.5B-v3.0-Instruct Q8_0 | 1.70 GB | 1.6 s | 57 | 2.0 GB | 10/25 | 18 / 1 |
| **Qwen3-1.7B Q8_0** | 1.83 GB | 2.9 s | 129 | 2.9 GB | **15/25** | **25 / 0** |
| Qwen3-4B Q4_K_M | 2.50 GB | 8.1 s | 162 | 5.2 GB | 13/25 | 19 / 3 |
| Basal (basal-omni-pico) | not run | | | | | decision-head model: answers choices, does not transcribe values (model-basal.md); no use for field reading |

Per-token speed (0.6B, 4 threads, loaded machine): prompt about 37 tok/s, generation about 14 tok/s. A 1.7B model is
roughly 3x slower, so one 2-page scan costs 1.5-3 minutes here. That decides the design: the model is asked only when
a field is empty or weak, with the smallest useful context, behind a `when:` regex.
Failure modes seen: 0.6B invents values (5 quotes not in the text); 4B Q4 was not better than 1.7B Q8 on this task and
needs 5 GB; every model fails the first-charge id on all 5 docs when the charge line is lost by OCR (odw_0005) and
the 0.6B/1.5B models confuse signatories with attorneys.
**Choice: Qwen3-1.7B Q8_0** (Apache-2.0, 1.83 GB, <= 4B parameters, 2.9 GB RAM, best accuracy, no ungrounded answers).
The raw spike script and logs are in the coder's scratchpad; numbers above are copied from them.


## What was done
- `odw2json/llm/` (generic, no class names, AC-3 grep clean): `plan.py` (reads field-level `llm:` and the class-level
  `llm:` block of a recipe: scalar fields by output path, choices from a dictionary with `also` companion field,
  groups = lists of items aligned by a key field, `when` regex gate, `override`), `prompt.py` (prompt + JSON schema built
  from the plan, every value is `{value, quote}` and nullable), `grounding.py` (folded letters+digits skeleton, quote must
  be found in the page text the model saw, value must lie inside its quote), `reader.py` (merge policy, decisions),
  `runtime.py` (llama-cpp-python adapter behind a `Runtime` interface, grammar from the JSON schema, lazy load, no network),
  `extractor.py` (`LlmExtractor` wraps the recipe engine behind the normal Classifier/Extractor interface; if the model
  or runtime is missing it logs once and returns the recipe output), `fetch.py` (`python -m odw2json.llm.fetch`, sha256
  checked, registry of 4 Apache-2.0 models; the CLI also downloads on first use of the `llm` profile, never fails the run).
- Merge policy (spec-extraction pattern): null -> fill (confidence 0.8, rule `llm:<model>`, page + snippet); equal ->
  agreed; recipe value with confidence 1.0 -> never replaced (not even asked); OCR-confidence values (0.9) replaced only
  on `override: true` fields; checksum-invalid LLM value on a null field kept only at confidence 0.4; ungrounded,
  unknown choice, or an item that is not among the recipe's items -> dropped and traced (`ODW2JSON_LLM_TRACE=file.jsonl`).
- Recipes: schema extension (`llmAsk`, `llmBlock`), `llm:` blocks in odwolanie (first-charge id + label, BZP, procedure
  number, two party names), pelnomocnictwo (attorney list with PESEL, `when: pesel`), przelew (title). Ignored by the
  `ocr` profile. Docs: `docs/LLM.md`, a section in `docs/ADDING_A_DOCUMENT_CLASS.md`.
- Wiring (after merging T012's branch, which contains main at T015): `profiles/llm.yaml` (reader kind `llm` registered in
  `profiles.READERS`), `factory.extractor_for`, one call in `cli.py`, `requirements-llm.txt`, Dockerfile build arg
  `LLM_MODEL=qwen3-1.7b`. The `ocr` default is unchanged; weights in gitignored `models/`.
- Tests: `tests/test_llm_reader.py` (22 tests with a fake runtime: grounding, never-override, override, validator,
  choices, group alignment, unreadable answer, no call when nothing is needed, missing model). T012's placeholder test
  "reader slot not installed fails loudly" became "unknown reader kind fails loudly" + "llm kind is registered".

Only 4 of 60 heldout and about 4 of 30 scan documents trigger a model call (all others have nothing the recipes left
empty and opt in); p50 is unchanged, p95 is one model call (2 minutes on this machine). RAM 5.1 GB at 2 workers (< 10 GB).
Unit tests (AC-1): 231 OK. Direct run on the scans with the model (`.house`-external trace, qwen3-1.7b): PESEL filled
and exact for pel_0004 (69102340858), pel_0007 (90082629103), pel_0009 (68091502944 and 82070226436); these four fields are
the whole gain (+0.0068 F1).

Grounded and rejected examples (decisions from the run on the scans):
- filled, grounded: `pelnomocnicy[0].pesel = '69102340858'`, quote `PESEL: 69102340858` found on page 1 of pel_0004
  (evidence rule `llm:Qwen3-1.7B-Q8_0`, snippet kept, confidence 0.8).
- rejected, not among the recipe's items: in pel_0007 the model listed `Dorota Grabowska` and `Lukasz Sosnowski` as
  attorneys (they are the principal's board members, quote "Prezes Zarządu - Lider Konsorcjum"); the recipe already had the
  real attorney, so they were not added.
- rejected, no answer: odw_0005 first-charge id and procedure number (the OCR lost those lines, the model correctly said
  null instead of guessing).
- ungrounded drops are unit-tested (`test_ungrounded_quote_is_dropped`, `test_value_missing_from_its_own_quote_is_dropped`);
  in the spike the 0.6B model produced 5 answers whose quote was not in the text, the chosen 1.7B produced none.

## Result vs acceptance
- AC-1 pass (231 tests). AC-2 pass (`bench: 2 profiles x 3 sets ok`). AC-3 pass (grep clean).
- AC-4 (manual, for the judge): `llm` beats `ocr` on skany by **+0.007, not the +0.05 target**: the scans were already at
  0.9639 (T014), so only 0.036 of headroom existed and most of it (OCR dropped whole lines, wrong accents, a PL prefix kept in
  gold) is not recoverable from the text. Does not lose on heldout or negatives; peak RAM 5.1 GB < 10 GB; Qwen3-1.7B
  (1.7B <= 4B, Apache-2.0); offline after the one-time download; every LLM value has evidence with a quote found in the
  page text. Honest verdict: the model is correct and safe but earns +0.007 F1 for 2 minutes per triggered document on
  this laptop, so `llm` stays opt-in (D-021); `ocr` remains the default.

## Tested and did not work
- Letting the model fill party roles on every scan (`override: true` on names) was designed but not enabled: it would
  put a 2-minute call on every OCR document for no measured gain (names are already 1.00 on scans).
- Asking for BZP number and transaction number on every document: all 11 asked cases had gold null, i.e. pure cost and
  hallucination risk. Added `when:` gates (`bzp`, `tytu|szczegol|opis`) and removed transaction number.
- Qwen3-0.6B (invents values), Qwen3-4B Q4_K_M (not better than 1.7B, 5.2 GB, 162 s/doc), Bielik-1.5B (10/25, fastest
  at 57 s/doc but misses the PESEL and signers), 8 threads on a 4-core CPU (slower than 4). A first spike prompt of 7000 chars was
  trimmed to 4500.
- Basal was not run: it is a decision-head model (choice among given options), it cannot transcribe PESEL or names.
